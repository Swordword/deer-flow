# 技术方案抽取规则

将 PRD 转换成技术文档前，先按本规则建立“需求事实 -> 实现影响 -> 验证方式”的链路。

## 输入可信度

| 来源 | 用途 | 注意事项 |
| --- | --- | --- |
| `product-specs/.../prd.md` | 当前需求事实和验收标准 | 最高优先级；不要擅自扩范围 |
| `product-specs/.../open-questions.md` | 未确认问题 | 阻塞型问题未关闭时，不能输出最终方案 |
| `llm-wiki/` | 长期业务上下文 | 只能作为背景和约束，不替代当前 PRD |
| 当前代码和测试 | 实现位置、现状行为、测试命令 | 技术方案的代码路径必须有证据 |
| 历史 PR/MR | 类似实现参考 | 只能作为参考，不自动成为当前规则 |

## 影响范围抽取

从 PRD 中提取：

- 页面/入口：路由、菜单、按钮、表单、列表、详情页。
- 用户动作：查询、创建、编辑、删除、审批、导入、导出。
- API：新增、修改、废弃、透传参数、响应字段。
- 数据：字段、枚举、状态、索引、历史数据兼容。
- 权限：角色可见性、操作权限、后端鉴权。
- 异常：错误提示、空态、接口失败、未知枚举值。
- 验收：需要被单测、集成测试、E2E 或人工验证的行为。

## 代码链路写法

优先写成：

```text
前端页面/组件:
- frontend/src/...

API 调用:
- frontend/src/... -> GET /api/...

后端入口:
- backend/...

业务逻辑:
- backend/...

数据访问:
- backend/...

数据结构:
- migrations/... 或 models/...
```

如果只找到部分链路，不要补全猜测；写入“待确认/待定位”。

## 设计点分类

每个重要设计点按以下格式整理：

```md
### <设计点>

- 需求来源：
- 当前实现：
- 方案：
- 兼容性：
- 测试：
- 风险：
```

## 阻塞型问题

这些问题未确认时，不应输出最终可开发方案：

- PRD 的核心验收标准冲突。
- 权限边界不明确且涉及敏感操作。
- 数据删除、资金、隐私、生产配置影响不明确。
- 不知道目标模块或仓库范围。
- 需求要求修改的核心业务对象无法在代码中定位。

非阻塞问题可以作为假设进入方案，但必须在风险清单中标明。

## 测试映射

每条验收标准至少映射一种验证方式：

| 验收类型 | 推荐测试 |
| --- | --- |
| 纯函数/规则 | 单元测试 |
| API 参数/响应 | 后端集成测试或契约测试 |
| 页面交互 | 前端组件测试或 E2E |
| 权限 | 后端鉴权测试优先，前端显示测试补充 |
| 数据迁移/兼容 | migration 测试、回归 SQL、人工数据核对 |

如果测试命令未知，写“待确认测试命令”，不要编造。
