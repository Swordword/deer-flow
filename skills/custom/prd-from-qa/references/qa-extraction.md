# 问答记录抽取规则

将问答、会议纪要、聊天记录整理成 PRD 前，先按本规则提取需求事实。

## 信息分类

| 分类 | 含义 | 写入位置 |
| --- | --- | --- |
| 已确认事实 | 来源材料明确说过，且没有冲突 | `prd.md` 正文 |
| 合理推断 | 可从上下文推导，但未被直接确认 | `prd.md` 的“假设与约束”或 `open-questions.md` |
| 待确认问题 | 缺失、模糊、影响验收的问题 | `open-questions.md` |
| 冲突信息 | 两处来源说法不一致 | `open-questions.md`，标明冲突点 |
| 长期知识候选 | 可能应沉淀到 llm-wiki 的长期规则 | `prd.md` 的“后续沉淀” |

## 抽取维度

从问答中提取：

- 背景：为什么要做，当前痛点是什么。
- 目标：这次需求要改变什么结果。
- 用户：谁会使用或受影响。
- 场景：用户在什么上下文中触发需求。
- 范围：本次做什么，不做什么。
- 产品行为：页面、按钮、字段、状态、提示、流程变化。
- 规则：权限、状态流转、校验、数据可见性、异常处理。
- 数据：新增/变更字段、统计口径、导入导出、埋点。
- 兼容：历史数据、旧入口、灰度、回滚。
- 风险：隐私、资金、权限、删除、生产配置、外部依赖。
- 验收：可人工或自动验证的通过条件。

## 冲突处理

遇到冲突时：

1. 不要自行选择一个版本写成事实。
2. 在 `open-questions.md` 写清楚冲突来源。
3. 在 PRD 对应章节用“待确认”标记。

示例：

```md
- 待确认：账号状态筛选是否包含“已注销”。问答 A 提到只包含“正常/冻结”，问答 B 提到需要覆盖所有状态。
```

## 验收标准写法

优先使用 Given/When/Then 风格，也可以使用中文条件句。

```md
- 当运营在用户列表选择“冻结”状态并点击查询时，列表只展示账号状态为“冻结”的用户。
- 当未选择状态筛选时，系统保持现有默认查询结果不变。
- 当接口返回状态枚举不存在的值时，前端展示“未知状态”，并不影响列表渲染。
```

避免：

```md
- 状态筛选正常。
- 页面体验好。
- 查询逻辑正确。
```

## 问题写法

问题必须具体、可回答，并说明为什么需要确认。

好：

```md
- “冻结”用户是否允许出现在导出结果中？这会影响导出接口和验收范围。
```

不好：

```md
- 请补充导出逻辑。
```
